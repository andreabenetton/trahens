# B1.1 scope: authenticated adjacent-link establishment

**Status:** Proposed scope. Nothing here is implemented. Six decisions in
section 3 need a sign-off before implementation starts; each carries a
recommendation.
**Parent:** `spec/network-bootstrap-b1.md`, stage B1.1 (section 14).
**Prerequisite decisions already taken:** ADR 0041 (v1.7 route channel),
ADR 0042 (link epoch strategy).

---

## 1. What B1.1 is for

P1 assumes an adjacent authenticated graph already exists: every link is
configured with a pre-shared 32-byte base key and a 32-bit epoch, and W2 derives
its directional keys from those. Everything W2 guarantees therefore rests on an
operator keeping `(base key, epoch)` unique across process lifetimes, which
nothing enforces. The external review raised this as TR-02, the P1 profile now
states it as an operating precondition, and ADR 0042 concluded that the only
mechanism that actually retires the hazard is fresh, session-derived traffic
keys — which needs a handshake.

B1.1 replaces the pre-shared base key with an authenticated key exchange between
manually named peers. After B1.1:

- every process session derives its own directional W2 keys;
- the epoch is derived from the handshake, so restarting into a used epoch is
  impossible rather than forbidden;
- the profile set both ends run is negotiated inside the authenticated
  transcript, so a downgrade fails authentication instead of succeeding quietly;
- rekey before sequence exhaustion is a protocol operation rather than an
  operator task.

B1.1 does **not** make Trahens bootstrap autonomously. Peers are still named by
configuration. That is deliberate: it isolates the key-exchange problem from the
discovery and admission problems, which have different adversaries.

## 2. Boundary

### In scope

| Item | Source |
|---|---|
| Mutually authenticated handshake between two peers who each hold the other's pinned static public key | B1 §8 |
| Transcript-bound profile negotiation with downgrade resistance | B1 §8 |
| Session-derived directional W2 keys, epoch, and an export key for rekey chaining | B1 §8, §9, ADR 0042 |
| Rekey with bounded old-key overlap and zeroization | B1 §9 |
| Restart safety as a consequence of the above, not a separate mechanism | B1 §9 |
| Registry bounds for handshake contexts, public-key operations, duration, retransmission, failed attempts, and rekey overlap | B1 §13 |
| Tests for restart, rekey, replay, downgrade, and exhaustion | B1 §14 |
| A minimal peer manifest carrying `(peer id, address, pinned static key)` | B1.0, folded in only to the extent B1.1 needs it |

### Out of scope

| Item | Where it belongs |
|---|---|
| Peer discovery, seeds, multicast, invitation delivery | B1.2 |
| Gateway-service and directory-root discovery | B1.3 |
| Certificates, federation roots, revocation | B1-Federated identity model |
| Accepting unknown peers, Sybil resistance, cookies for opportunistic admission | B1-Opportunistic, B1.2 |
| Signed manifest format beyond the three fields above | B1.0 proper |
| Reply-path key privacy (TR-10), private directory (D1) | Unaffected by this work |
| Post-quantum key exchange | Separate decision; the handshake framework chosen below can carry a hybrid later |

### Compatibility consequence

Removing the pre-shared base key changes what travels on a link before any W2
cell. That is a wire change, so B1.1 lands as **Core v1.8** with v1.7 retained
frozen, following the v1.7 precedent. Every harness invocation, the multi-host
runner, and the `--external-endpoint` interop path change: a third-party
initiator must implement the handshake to interoperate. This is the largest
practical cost of B1.1 and should be accepted knowingly.

## 3. Decisions requiring sign-off

Each decision has a recommendation. The recommendations are consistent with one
another; picking a different option in one may reopen others.

### D1. Handshake framework and pattern

**Options.** (a) A Noise pattern. (b) A TLS-1.3-derived construction. (c) A
custom Diffie-Hellman protocol.

**Recommendation: Noise, pattern `KK`.** B1 §8 already rules out (c). TLS
brings certificates, record layering and negotiation machinery that overlap
with M2/W2 rather than complement them. Noise gives exactly the shape B1 §8
describes: a transcript hash that binds every payload, two directional
CipherStates on completion, and a documented security model per pattern.

`KK` is the pattern where both parties know the other's static key before the
first message, which is precisely "manually named peers". It authenticates both
sides in one round trip and gives the initiator's first message forward secrecy
against later static-key compromise for everything after it. `IK` and `XX` are
the extension paths for B1.2 and B1-Opportunistic respectively, where the
responder does not know the initiator in advance; choosing `KK` now does not
foreclose them.

### D2. Curve and static-key separation

**Options.** (a) Instantiate Noise over ristretto255, which the crate already
has. (b) Add X25519 via libsodium and use the standard
`Noise_KK_25519_ChaChaPoly_SHA256` instantiation.

**Recommendation: (b).** Noise's analysis is abstract over the DH group, so
(a) is likely sound, but it is a non-standard instantiation that every reviewer
will have to reason about afresh, and "reviewed framework" is the whole point.
libsodium's `crypto_scalarmult` is already linked; the Python reference gets
X25519 from `cryptography`, already a dependency. ristretto255 stays where the
reply path needs its group structure.

Static identity keys for the handshake should be **separate X25519 keys**, not
the gateway's Ed25519 signing key converted through the birational map. Key
reuse across a signature scheme and a DH scheme is a standing reviewer
objection with no benefit here.

### D3. Profile negotiation and downgrade resistance

**Recommendation.** The initiator's first payload carries its complete offered
set: protocol versions, W2/T1/T2 profiles, eligibility suites, and resource
class. The responder's payload carries its selection. Both payloads are
encrypted and, because Noise mixes every payload into the transcript hash, any
modification fails the final authentication. The responder aborts if its
selection is not a subset of the offer; the initiator aborts if the selection
names anything it did not offer. Suites the registry marks retired or disabled
are rejected at parse, before negotiation, so they cannot be offered at all.

There is no "downgrade to the pre-shared-key path": B1.1 removes that path
rather than keeping it selectable, because a selectable legacy path is a
downgrade target by definition.

### D4. Epoch and key derivation

**Recommendation.** Per ADR 0042, derive the epoch from the handshake: the first
four bytes of an HKDF expansion over the final transcript hash under a
registry-listed domain. Both ends compute it identically; uniqueness follows
from both ephemeral contributions being fresh. The two directional W2 keys are
the two Noise CipherStates. A third expansion under a separate domain yields the
export key used to chain rekeys. All domains live in the v1.8 registry.

**Consequence for ADR 0042.** That ADR recommended a persistent high-water epoch
check as a detector alongside the key-derived mechanism. With fresh
session-derived keys the detector guards against nothing: a repeated epoch under
*different* keys is harmless, and a repeated epoch under the *same* keys requires
the same ephemerals, which is an RNG failure — and that path now fails closed
(`88cade6`). The recommendation here is to **drop the detector** and amend ADR
0042 to say so, rather than build a mechanism whose only job is to sit beside
one that already covers it.

### D5. Rekey mechanism

**Options.** (a) A full re-handshake with fresh ephemerals, chained to the prior
session through the export key. (b) A symmetric ratchet over the current key.

**Recommendation: (a).** A re-handshake gives fresh Diffie-Hellman per rekey,
which a ratchet does not, and chaining through the export key stops an
unrelated handshake from being spliced in as a rekey. It is also the simpler
thing to reason about in a model checker. Triggers: a registry-bounded cell
count or elapsed time, whichever first, well below sequence exhaustion. Old
receive keys stay valid for a registry-bounded overlap and are then zeroized;
old send keys are zeroized at the switch.

### D6. Implementation strategy and DoS posture

**Options for the Noise state machine.** (a) Depend on the `snow` crate. (b)
Implement `KK` by hand against the Noise specification, using `snow` only as a
dev-dependency to generate cross-check vectors.

**Recommendation: (b).** This repository's discipline is registry-driven,
vector-checked and dependency-minimal, and a hand-written `KK` over existing
primitives is a few hundred lines. The reviewed artefact is the Noise design;
cross-checking against an independent implementation's vectors is what makes
the hand implementation trustworthy.

**DoS posture.** Between manually named peers, a stateless cookie round trip is
not worth its complexity: the responder performs one DH per first message, and
B1 §13's bounds on handshake contexts and public-key operations per source and
interval cap the cost. Cookies belong with B1.2, where the responder does not
know who is knocking. B1.1 needs a bounded handshake-context table and a
per-peer rate limit, both registry-sized, and nothing more.

## 4. Deliverables

Grouped as they would be committed. Each group is independently green.

**Group 1 — profile and reference.**
- `spec/protocol-registry-v1.8.json` with handshake record types, domains
  (handshake, epoch, export, rekey), widths, and the §13 limits.
- `spec/link-handshake-b1.md` as a normative-candidate spec: message flow,
  payload encodings, transcript composition, derivation, rekey, error
  handling, and bounds.
- Core/messages/state-machines/invariants/resource-accounting/p1-prototype at
  v1.8, with v1.7 retained frozen; `check_repo.sh` and the generators updated
  as they were for v1.7.
- Python reference in `simulator/trahens_crypto/b1.py`, and a vector generator
  whose output the Rust side must match byte for byte.

**Group 2 — handshake crate.**
- `crates/link-handshake-b1`: `KK` state machine, negotiation, derivation,
  rekey chaining. Unit tests plus the published vectors.

**Group 3 — integration.**
- `LinkConfig` loses `base_key` and `epoch`, gains a static keypair and the
  peer's pinned static public key. `spawn_link` runs the handshake to completion
  before the W2 loop starts; no P1 state is reachable before that.
- Binaries take `--static-seed` and `--peer-static` in place of `--key` and
  `--epoch`. Harness and multi-host runner generate keys per run.
- Handshake records are padded to the full 1,052-byte cell so invariant 1 holds
  from the first record on a link.

**Group 4 — assurance.**
- The five harness scenarios B1 §14 names: *restart* (a cell recorded in one
  session is refused in the next, same pinned keys); *rekey* (traffic continues
  across the switch, old key refused after overlap); *replay* (a replayed first
  message costs the responder one bounded DH and nothing else); *downgrade* (a
  stripped profile or an injected retired suite fails authentication);
  *exhaustion* (a full context table refuses cleanly, failed attempts back off).
- `formal/B1Rekey.tla` for the overlap state machine, run by the existing CI
  formal job.
- Paper and evidence-boundary updates; B1 §8–9 promoted from "should" to the
  normative spec.

## 5. Staging and effort

Groups 1 through 4 in order, each a green commit series against `make check`.
Roughly one to two weeks of focused work. The time goes into group 3's harness
churn and group 4's rekey scenarios, not the cryptography; the handshake itself
is the well-understood part.

## 6. What B1.1 leaves open

- **KK first-message replay.** Bounded by §13 limits, not eliminated. B1.2's
  cookie mechanism eliminates it; B1.1 should not pretend to.
- **Identity model.** Pinned static keys are the B1-Invitation model with the
  invitation delivered out of band. Federated and opportunistic models remain
  unaddressed.
- **Third-party interoperability.** The `--external-endpoint` path and
  `check_external_codec.py` become harder to satisfy: an external implementer
  needs the handshake before they can speak. The published vectors are what
  makes that tractable.
- **TR-10 and D1.** Untouched. B1.1 is about the link, not the route.
