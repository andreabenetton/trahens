# B1.2 scope: seeded peer discovery and stateless admission

**Status:** Decided scope, 6 September 2026. All seven decisions in section 3
were taken as recommended and are recorded in ADR 0045. D7's conditional check
has since been performed and passed, so B1.2 is additive to v1.8. Of the
deliverables, only the misbehaving test peer in group 1 is implemented.
**Parent:** `spec/network-bootstrap-b1.md`, stage B1.2 (section 14), drawing on
sections 5, 6, 7 and 13.
**Prerequisite decisions already taken:** ADR 0043 (B1.1 handshake), ADR 0044
(first-message authentication under `psk0`).

---

## 1. What B1.2 is for

B1.1 authenticates a link between two peers that already hold each other's
address and static public key in a manifest. That manifest is what P1's
bootstrap boundary still rests on: the prototype demonstrates route bootstrap
over a named peer set, not autonomous network bootstrap.

B1.2 removes the requirement that a peer be named in advance. A node learns
candidate peers it was not configured with, from signed seeds and optionally
from the local link, and admits them under bounds rather than under prior
acquaintance.

The reason this is a stage of its own, and not a widening of B1.1, is that
**ADR 0044's first-message defence cannot follow it.** B1.1 refuses a forged
first message because both peers can compute a static-static value offline from
the manifest. A peer with no manifest entry supplies no such value, so the
handshake is back to answering strangers — the exact exposure ADR 0044 closed,
reopened by construction rather than by oversight. B1.2 is therefore first a
question about what replaces that defence, and only second a question about
discovery.

Two further consequences follow from accepting unknown peers, and both should
be understood before any code is written:

- **A listening socket appears.** Today each link owns a UDP socket connected to
  its peer, so the kernel discards everything from any other address before the
  process sees it. Discovery needs a socket that accepts from anywhere.
- **Four registry bounds stop being free.** `link-handshake-b1.md` section 8
  records that `max_handshake_contexts` has nothing to count in P1, and that
  `handshake_pubkey_ops_per_interval`, `max_failed_handshakes_before_backoff`
  and `handshake_backoff_ms` are satisfied by the topology rather than enforced.
  Every one of those becomes a live requirement the moment the listening socket
  exists. B1.2 must implement them, not inherit them.

## 2. Boundary

### In scope

| Item | Source |
|---|---|
| Signed seed manifests naming candidate peers | B1 §14 (B1.2) |
| A bounded candidate-peer cache, fed by every discovery source | B1 §6, §14 |
| A stateless admission front end: cookie bound to source, time window and offered parameters, validated before any public-key operation | B1 §7 |
| A first-message defence for peers with no manifest entry, replacing what ADR 0044 gives named peers | ADR 0044, this document §3 D2 |
| Enforcement of `max_handshake_contexts`, `handshake_pubkey_ops_per_interval`, `handshake_interval_ms`, `max_failed_handshakes_before_backoff`, `handshake_backoff_ms` | B1 §13; currently unenforced by construction |
| A discovery advertisement encoding carrying only the fields B1 §6 permits | B1 §6 |
| Optional local-link discovery, behind an explicit selection | B1 §14 |
| Per-joiner single-use invitations, promoted to a pinned static key on success | ADR 0046 D8 |
| Minimal revocation: a spent-invitation list, and removal of a pinned key at the node that admitted it | ADR 0046 D9 |
| Adversarial scenarios: source spoofing, cookie exhaustion, context exhaustion, malicious seeds | B1 §14 (B1.4, pulled forward for what B1.2 introduces) |

### Out of scope

| Item | Where it belongs |
|---|---|
| Gateway-service advertisement, directory-root documents | B1.3 |
| Endpoint descriptor lookup, private directory | D1, unaffected |
| Certificates, federation roots, and revocation propagated between nodes | B1-Federated identity model; signed revocation documents belong with B1.3's roots |
| Sybil resistance in any strong sense | Needs a cost or reputation mechanism; see §6 |
| Reputation, transit incentives, abuse adjudication | Outside B1 entirely |
| Changing M2, W2, T1, T2 or any route-discovery encoding | Unaffected: B1.2 adds a datagram type, it does not alter existing ones |

### Compatibility consequence

B1.2 adds a discovery datagram alongside W2 cells and B1.1 handshake records on
the same port, so a receiver needs a third discriminator. B1.1 records begin
with a zero byte and derived epochs have their top bit set, which is what
already separates those two; the discovery type must fit that scheme without
disturbing it.

Whether this warrants a new Core profile is **decision D7 below and is not
assumed here**. It plausibly does not: no existing encoding changes, and a node
that never enables discovery behaves exactly as a v1.8 node does. That is a
weaker claim than v1.7 and v1.8 could make, and it should be tested against the
registry rather than asserted.

## 3. Decisions requiring sign-off

**All seven were taken as recommended on 6 September 2026 and are recorded in
`docs/adr/0045-b1.2-scope-decisions.md`, which is authoritative.** The
reasoning below is retained as the argument that produced them.

Two further decisions surfaced when D2 came to be implemented and are recorded
in `docs/adr/0046-invitation-scoping-and-revocation.md`: **D8**, invitations are
per-joiner, single-use, and promote to a pinned static key on success; and
**D9**, minimal revocation lands in this stage rather than none of them.

Each decision has a recommendation. D1 and D2 are coupled: choosing the
opportunistic model in D1 removes the option recommended in D2.

### D1. Which identity and admission model B1.2 targets first

**Options.** (a) B1-Invitation: a joining node proves possession of a
short-lived invitation secret. (b) B1-Opportunistic: previously unknown peers
are accepted under limits alone. (c) B1-Federated: certificates under one or
more roots.

**Recommended: (a) B1-Invitation.** It is the model that keeps ADR 0044's
construction alive. An invitation secret is a shared value both ends hold
before the first message, which is precisely what the `psk0` key needs; the
derivation changes its input from the static-static value to the invitation,
and the first-message property survives unchanged. That is a small,
well-understood delta against a construction now cross-checked against an
independent Noise implementation.

(b) is where the real difficulty lives and should be a later stage, not this
one. With no shared secret of any kind, nothing can authenticate a first
message and the cookie gate of D2 becomes the only defence — a
denial-of-service control, explicitly not an identity proof. (c) brings
certificate handling, chain validation and revocation, none of which the
codebase has, and creates visible administrative domains that cut against the
privacy goals.

Deciding (a) does not close (b): the discovery, cache and cookie machinery below
is what (b) will need, and building it under (a) means building it where a
working first-message defence still exists to compare against.

### D2. First-message defence for a peer with no manifest entry

**Options.** (a) Derive the `psk0` key from an invitation secret, as D1(a)
allows. (b) A stateless cookie round trip before any handshake state is
allocated. (c) Proof of work. (d) Accept the exposure under bounds alone, as
B1.1 did before ADR 0044.

**Recommended: (a) as the mechanism, (b) as the floor.** Under B1-Invitation
the invitation keys `psk0` and a forged first message is refused before any
Diffie-Hellman, exactly as today. The cookie should still exist, because it is
what bounds the cost of *reaching* that check from a spoofed source, and
because it is what B1-Opportunistic will have to fall back on.

(c) is rejected: proof of work penalises legitimate constrained nodes as much
as attackers and gives no property the cookie does not. (d) is rejected because
this session's work established it was never necessary — the exposure was a
consequence of not using a shared value that was already available, and B1.2
should not reintroduce it as a default.

### D3. Cookie construction

**Options.** (a) HMAC over (observed source tuple, time window, offered
parameters) under a rotating responder secret. (b) A DTLS-style
`HelloVerifyRequest` equivalent. (c) An encrypted token carrying responder
state.

**Recommended: (a).** It satisfies B1 §7 directly: expires with the window,
authenticated under a responder secret, binds the parameters offered so far,
reveals no long-term secret, and is checkable before any public-key operation.

Two properties need explicit treatment rather than assumption. **Rotation:**
two overlapping window secrets, so a cookie issued at a boundary still verifies,
with the older zeroized on rotation — the same shape as the B1.1 rekey overlap
already modelled in `formal/B1Rekey.tla`. **Linkability:** a cookie bound to a
source address is a correlation handle for the window it lives in. It must not
be reusable across windows and must not appear in anything a third party
observes twice; B1 §7's "avoid creating a reusable tracking token" is a
requirement, not advice, and needs a stated argument that the chosen lifetime
meets it.

### D4. Discovery advertisement encoding

**Options.** (a) A fixed-width datagram padded to the cell length, as B1.1
records are. (b) A variable-length datagram. (c) Reuse M2 inside a W2 cell.

**Recommended: (a).** (c) is circular — a W2 cell needs a link, and discovery is
what precedes one. (b) leaks a length signal on a datagram sent before any
encryption exists, and makes captures non-uniform, which the harness's
1,052-byte assertion currently relies on. Fixed width costs bandwidth on a
message sent rarely, and buys a capture stream an observer cannot separate by
size.

The contents are constrained by B1 §6 and should be taken from it verbatim
rather than re-derived: version, short-lived key, supported modes and profiles,
coarse capacity class, expiry, proof, optional cookie. It must carry no
descriptor, capability, route label, or stable network-wide identifier.

### D5. Short-lived advertisement keys and the transition to identity

**Options.** (a) Advertise under the long-term static key. (b) Advertise under a
short-lived key with a signed transition to the admission identity. (c)
Advertise under a short-lived key with no transition, and let the handshake
establish identity.

**Recommended: (b).** (a) copies a stable identifier into every unauthenticated
datagram, which B1 §6 warns against and which makes passive correlation trivial.
(c) leaves nothing binding the advertisement to the peer eventually admitted, so
an advertisement can be replayed by anyone. (b) is what B1 §6 describes, and the
signed transition is the part most likely to be got wrong: it must bind the
short-lived key to the admission identity in a transcript the handshake then
covers, or the two halves can be attacked separately.

### D6. Discovery must not allocate handshake state

**Recommended, and treated as a constraint rather than an option.** B1 §6 says
not to mix discovery with admission. Concretely: the discovery path writes only
into the bounded candidate cache and never allocates a handshake context, never
performs a public-key operation, and never causes a socket to be created. A
separate, explicitly bounded step consumes cache entries and decides whether to
attempt admission.

This is what keeps `max_handshake_contexts` meaningful. If discovery could
allocate, the cache bound and the context bound would be the same bound, and an
attacker filling one would fill the other.

### D7. Whether B1.2 needs a new Core profile

**Options.** (a) A new profile, following v1.7 and v1.8. (b) An additive change
to v1.8: a new datagram type and new registry entries, with no existing encoding
altered.

**Recommended: (b), subject to checking. Checked and settled: (b).** No M2, W2,
T1 or T2 encoding changes, and a node with discovery disabled speaks exactly
what a v1.8 node speaks. The check that decided it was whether the discovery
datagram can be discriminated from a W2 cell and a B1.1 record without
ambiguity, and whether any registry value an existing binding reads has to
change. Both passed: the first byte range `0x01`–`0x7f` is reachable by neither
existing type and is now reserved in `link-handshake-b1.md` section 3, and
adding registry entries was shown to leave every conformance artifact
byte-identical. ADR 0045 records the evidence.

## 4. Deliverables

Grouped as they would be committed, each group independently green against
`make check`.

**Group 1 — bounds that are currently free.**
- Enforce `max_handshake_contexts`, `handshake_pubkey_ops_per_interval` with
  `handshake_interval_ms`, and `max_failed_handshakes_before_backoff` with
  `handshake_backoff_ms`, against a source rather than a configured peer.
- Adversarial tests for each, which the harness cannot currently write because
  it has no way to spawn a misbehaving peer. This group therefore also delivers
  that: a test peer that sends malformed, replayed and flooded records.
- Correct `link-handshake-b1.md` section 8, which currently explains why these
  bounds have nothing to count.

Doing this first means the exposure is bounded before anything opens a
listening socket, rather than after.

**Group 2 — cookie and admission front end.**
- Cookie construction, rotation with overlap, and validation before any
  public-key operation.
- The `psk0` derivation from an invitation secret (D1a, D2a).
- Vectors for both, generated from a Python reference and reproduced by the Rust
  side, as B1.1 and the route channel now are.

**Group 3 — discovery.**
- Advertisement encoding, signed seed manifest format, the bounded candidate
  cache, and the separation in D6.
- Optional local-link discovery behind an explicit selection.

**Group 4 — assurance.**
- Harness scenarios for source spoofing, cookie exhaustion, context exhaustion,
  malicious and expired seeds, and an advertisement replayed by a third party.
- A formal model of the cookie window overlap, if D3's rotation is accepted;
  `formal/B1Rekey.tla` is the precedent and the shape is the same.
- Paper and evidence-boundary updates: the bootstrap boundary moves, and the
  claim that P1 demonstrates route bootstrap over a *named* peer set stops being
  accurate.

## 5. Staging and effort

Groups 1 through 4 in order. Group 1 is worth doing whether or not the rest
proceeds, because it closes a gap that exists today in principle and would exist
in practice the moment discovery lands.

Larger than B1.1. The cryptography is smaller — a cookie is an HMAC — but the
work is in the parts B1.1 did not have: a listening socket with an adversarial
input surface, state bounded against an attacker rather than against a
configured peer, and a test peer that misbehaves on purpose. Estimating beyond
"more than B1.1's one to two weeks" would be a guess.

## 6. What B1.2 leaves open

- **Sybil resistance.** B1 §5 is explicit that the opportunistic model cannot
  claim it without an additional cost or reputation mechanism, and B1.2 adds no
  such mechanism. Under B1-Invitation the invitation is the cost, which is a
  deployment property rather than a protocol one.
- **B1-Opportunistic itself.** D1 recommends deferring it. Until it is taken,
  Trahens admits only peers that hold an invitation, which is a smaller claim
  than "autonomous bootstrap".
- **Gateway-service and directory-root discovery.** B1.3.
- **Revocation beyond one node.** ADR 0046 D9 brings minimal revocation into
  this stage, so an invitation cannot be spent twice and a pinned key can be
  removed. What remains open is everything network-wide: removing a key at one
  node says nothing to any other, and removal does not tear down a link already
  established. Propagation needs signed revocation documents and belongs with
  B1.3's roots. The word "revocation" should not be used unqualified about what
  this stage ships.
