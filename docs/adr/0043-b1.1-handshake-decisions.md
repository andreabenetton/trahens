# ADR 0043: B1.1 handshake decisions

## Status

Accepted, 5 September 2026. Amends ADR 0042. Implementation has not started;
this ADR fixes the design so that it can.

## Context

`docs/b1.1-scope.md` scopes stage B1.1 of the network bootstrap architecture:
replacing P1's pre-shared W2 base keys with an authenticated key exchange
between manually named peers. It put six decisions to the project owner with
recommendations. One was decided against the recommendation, which created a
seventh. This ADR records all seven and the consequences of the deviation, so
the implementation is built against a decision rather than a proposal.

## Decisions

**D1 — Noise pattern `XX`.** Recommended `KK`; decided `XX`. Neither peer needs
the other's static key before the first message; each presents its own inside
the handshake. For named peers this is security-equivalent to `KK` once the pin
check in D7 is applied, and it is the pattern B1.2 and the opportunistic
identity model need anyway, so widening admission later does not replace the
state machine.

**D2 — X25519 via libsodium, separate static keys.** The standard
`Noise_XX_25519_ChaChaPoly_SHA256` instantiation, so the reviewed analysis
applies without a bespoke DH argument. Each node's handshake identity is a
fresh X25519 static keypair; the Ed25519 signing key is not converted or
reused. ristretto255 remains the group for the reply path, which needs its
structure.

**D3 — Transcript-bound negotiation, no legacy path.** The initiator's full
offered set and the responder's selection are both encrypted payloads mixed
into the Noise transcript hash, so any tampering fails the final
authentication. Suites the registry retires or disables are rejected at parse.
The pre-shared-key path is removed rather than kept selectable.

**D4 — Handshake-derived epoch and keys; detector dropped.** The epoch is an
HKDF expansion over the final transcript hash under a registry domain. The two
directional W2 keys are the two Noise CipherStates. A third expansion yields the
export key. ADR 0042's persistent high-water detector is dropped: with
session-derived keys it guards against nothing that is not already an RNG
failure, and that path fails closed.

**D5 — Rekey by re-handshake chained through the export key.** Fresh
ephemerals per rekey; the export key from the prior session is mixed into the
new handshake so an unrelated exchange cannot be spliced in. Registry-bounded
triggers on cell count or elapsed time; bounded old-receive-key overlap, then
zeroization.

**D6 — Hand-written `XX` cross-checked against `snow` vectors; bounds, no
cookies.** The state machine is implemented against the Noise specification
over the primitives the crate already has, with `snow` as a dev-dependency to
generate independent vectors the implementation must match byte for byte. DoS
protection is B1 §13's registry bounds — handshake contexts, public-key
operations per source and interval, per-source rate — not a cookie round trip.

**D7 — Presented static key pinned against the manifest.** Created by D1. After
the peer's static key is authenticated inside the handshake it is compared with
the manifest entry for that peer id; a mismatch aborts before any key is
derived. Trust-on-first-use and unpinned acceptance were both rejected.

## Consequences of choosing `XX` over `KK`

These were not part of the recommended design and are accepted knowingly.

- **An extra half round trip.** `XX` is three messages; `KK` is two. Every link
  takes longer to come up by one one-way delay.
- **The responder's identity is exposed to active probes.** In `XX` the
  responder sends its static key in message 2 under a key derived only from the
  two ephemerals. Anyone able to send a first message therefore learns the
  responder's static identity before proving anything about themselves. `KK`
  transmits no static keys. The initiator's static key is sent in message 3
  under both ephemeral and static contributions and is not exposed. This is a
  property of the pattern, not of the implementation, and no B1.1 mechanism
  changes it; a deployment that must hide relay identities from unauthenticated
  probes needs B1.2's cookie gate in front of the responder or a different
  pattern.
- **Unsolicited first messages cost the responder DH work.** The responder
  answers message 1 before it knows who sent it. B1 §13's bounds cap this;
  cookies would eliminate it and are deferred to B1.2, where the same
  mechanism is needed for discovery.
- **Cookies become more justified than they were.** D6 still defers them, on
  the grounds that the cookie key rotation they need should be designed once,
  with B1.2. If probing cost or identity exposure turns out to matter before
  B1.2, that is the trigger to revisit D6, not to bolt a cookie onto a finished
  B1.1.

## Consequences generally

B1.1 is a wire change and lands as Core v1.8, with v1.7 retained frozen. Every
existing link invocation — harness, multi-host runner, and the
`--external-endpoint` interop path — changes, and a third-party implementer
must implement the handshake to interoperate. The published vectors are what
keeps that tractable.

The order of work is the four deliverable groups in `docs/b1.1-scope.md`:
registry and reference first, so no runtime code changes until the encoding and
vectors are fixed.
