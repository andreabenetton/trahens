# ADR 0045: B1.2 scope decisions

## Status

Accepted, 6 September 2026. Implementation has not started; this ADR fixes the
design so that it can. Depends on ADR 0044, whose first-message defence D1 and
D2 exist to preserve.

## Context

`docs/b1.2-scope.md` scopes stage B1.2: removing the requirement that a peer be
named in advance, by learning candidates from signed seeds and admitting them
under bounds. It put seven decisions to the project owner with recommendations.
All seven were decided as recommended. This ADR records them so the
implementation is built against a decision rather than a proposal.

The stage exists as a stage, rather than as a widening of B1.1, because ADR
0044's first-message defence cannot follow it unchanged. That defence refuses a
forgery because both peers compute a static-static value offline from the
manifest; a peer with no manifest entry supplies none. Accepting unknown peers
therefore reopens, by construction, the exposure ADR 0044 closed. D1 and D2 are
the answer to that, and everything else follows them.

## Decisions

**D1 — target the invitation model first.** A joining node proves possession of
a short-lived invitation secret. Recommended and decided.

An invitation secret is a value both ends hold before the first message, which
is what the `psk0` key needs. The derivation changes its input from the
static-static value to the invitation and the first-message property survives
unchanged — a small delta against a construction already cross-checked against
an independent Noise implementation.

The opportunistic model is deferred rather than rejected. It is where the real
difficulty lives: with no shared secret of any kind, nothing can authenticate a
first message. The discovery, cache and cookie machinery this stage builds is
what that model will need, and building it here means building it where a
working first-message defence still exists to compare against. Federated
identity was not taken: it brings certificate handling, chain validation and
revocation, none of which the codebase has, and creates visible administrative
domains that cut against the privacy goals.

**D2 — the invitation keys `psk0`; the cookie is the floor.** Recommended and
decided.

Under D1 the invitation keys the exchange and a forged first message is refused
before any Diffie-Hellman, exactly as today. The cookie still exists, because
it bounds the cost of *reaching* that check from a spoofed source, and because
it is what the opportunistic model will fall back on when it arrives.

Proof of work was rejected: it penalises legitimate constrained nodes as much
as attackers and gives no property the cookie does not. Accepting the exposure
under bounds alone was rejected because it was never necessary — the exposure
was a consequence of not using a shared value that was already available, and
this stage must not reintroduce it as a default.

**D3 — HMAC cookie over source tuple, time window and offered parameters, under
a rotating responder secret.** Recommended and decided.

It satisfies `network-bootstrap-b1.md` section 7 directly: expires with the
window, authenticated under a responder secret, binds the parameters offered so
far, reveals no long-term secret, and is checkable before any public-key
operation.

Two properties are part of the decision rather than left to implementation.
**Rotation** is two overlapping window secrets, so a cookie issued at a
boundary still verifies, with the older zeroized on rotation — the same shape
as the B1.1 rekey overlap already modelled in `formal/B1Rekey.tla`.
**Linkability** is a requirement, not advice: a cookie bound to a source
address is a correlation handle for the window it lives in, it must not be
reusable across windows, and the chosen lifetime needs a stated argument that
it meets section 7's "avoid creating a reusable tracking token".

**D4 — fixed-width advertisement datagram, padded to the cell length.**
Recommended and decided.

Reusing M2 inside a W2 cell is circular: a cell needs a link, and discovery is
what precedes one. A variable-length datagram leaks a length signal on a
message sent before any encryption exists, and makes captures non-uniform,
which the harness's 1,052-byte assertion relies on. Fixed width costs bandwidth
on a message sent rarely and buys a capture stream an observer cannot separate
by size. Contents are taken verbatim from section 6 rather than re-derived, and
carry no descriptor, capability, route label or stable network-wide identifier.

**D5 — short-lived advertisement key with a signed transition to the admission
identity.** Recommended and decided.

Advertising under the long-term static key copies a stable identifier into
every unauthenticated datagram, which section 6 warns against and which makes
passive correlation trivial. A short-lived key with no transition leaves
nothing binding an advertisement to the peer eventually admitted, so anyone can
replay one. The signed transition is the part most likely to be got wrong: it
must bind the short-lived key to the admission identity in a transcript the
handshake then covers, or the two halves can be attacked separately.

**D6 — discovery never allocates handshake state.** A constraint rather than an
option, and decided as such.

The discovery path writes only into the bounded candidate cache. It never
allocates a handshake context, never performs a public-key operation, and never
causes a socket to be created. A separate, explicitly bounded step consumes
cache entries and decides whether to attempt admission.

This is what keeps `max_handshake_contexts` meaningful. If discovery could
allocate, the cache bound and the context bound would be the same bound, and an
attacker filling one would fill the other.

**D7 — additive to Core v1.8, subject to a check.** Recommended and decided.

No M2, W2, T1 or T2 encoding changes, and a node with discovery disabled speaks
exactly what a v1.8 node speaks, so this does not obviously need the profile
bump v1.7 and v1.8 each took. The decision is conditional on a check that has
not been performed: whether the discovery datagram can be discriminated from a
W2 cell and a B1.1 record without ambiguity, and whether any registry value an
existing binding reads has to change. **If either fails, this becomes a new
profile** and the cost is the one v1.8 already paid. The check is owed before
the encoding is fixed, not after.

## Consequences

Four registry bounds stop being satisfied by construction. `link-handshake-b1.md`
section 8 records that `max_handshake_contexts` has nothing to count in P1, and
that `handshake_pubkey_ops_per_interval`, `max_failed_handshakes_before_backoff`
and `handshake_backoff_ms` hold because every socket is connected to its peer
rather than because anything enforces them. A listening socket ends all four
exemptions. Enforcing them is the first deliverable group in the scope, ahead of
any discovery code, and that group also delivers the misbehaving test peer the
harness has never had — which is why those bounds have stayed untested since
B1.1.

The bootstrap boundary moves, so the claim that P1 demonstrates route bootstrap
over a *named* peer set stops being accurate and the paper and evidence
boundary need updating with the stage rather than after it.

Sybil resistance is not obtained. Under D1 the invitation is the cost of entry,
which is a deployment property rather than a protocol one, and
`network-bootstrap-b1.md` section 5 is explicit that no strong claim is
available without a cost or reputation mechanism.

Revocation remains owned by no stage. Neither an invitation nor a static key can
be withdrawn once issued, and that matters more once peers are admitted without
an operator naming them.
