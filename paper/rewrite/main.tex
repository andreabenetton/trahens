\begin{abstract}
Route discovery can expose endpoint relationships and topology before an anonymous or encrypted data path is established. Trahens explores a control plane in which relays install short-lived, hop-local forwarding labels instead of learning or carrying a complete source route. This revision reduces the original 2020 concept to a bounded discovery core with duplicate suppression, candidate return, explicit route commitment, bidirectional label state, expiration, and resource limits. Global directory resolution and traffic-analysis-resistant link scheduling are treated as separate protocols or deployment profiles. The current version is a research specification and deterministic simulation baseline, not a production anonymity system. Its purpose is to make the design falsifiable: privacy claims are tied to explicit adversaries, and scalability claims are tied to reproducible experiments.
\end{abstract}

\section{Motivation}

Anonymous communication mechanisms are often evaluated after a path has already been selected. The process that discovers a destination, gateway, or route can itself reveal stable identifiers, local topology, timing relationships, and the set of nodes capable of reaching an endpoint. A route-discovery design should therefore account for privacy, authentication, availability, and resource amplification at the same time.

The original Trahens draft proposed local flooding, ephemeral route labels, reverse acknowledgements, gateways, beacons, authorities, batching, and cover traffic as parts of a new network stack. That design contained a useful central mechanism but combined too many unresolved layers. The present work separates a small route-state mechanism from stronger underlays and global resolution.

\section{Contributions of the current revision}

This revision contributes the following research artifacts:

\begin{enumerate}
  \item A bounded route-discovery core with explicit initiator, relay, and responder state machines.
  \item Hop-local random forwarding labels that are bound to one adjacent peer, direction, route generation, and expiration.
  \item A three-step candidate, commit, and ready process that separates route offers from active routes.
  \item Mandatory limits for hop count, fan-out, candidate count, relay state, retries, lifetimes, and cryptographic work.
  \item An adversary taxonomy that distinguishes active relays, colluding relays, partial link observers, global observers, and resource attackers.
  \item A deterministic simulator for discovery reachability, duplicate delivery, candidate collection, and state growth.
\end{enumerate}

\section{Scope}

Trahens Core discovers eligible service responders within a bounded graph radius and installs bidirectional forwarding state to one selected responder. It does not define global endpoint lookup, inter-domain policy, incentives, data-plane congestion control, or a replacement for IP. It can run over an existing authenticated transport during research and prototyping.

The baseline underlay protects confidentiality and integrity on one adjacent link. Padding, batching, and constant-rate scheduling are separate privacy profiles because they impose different latency and bandwidth costs and defend against different observers.

\section{Threat model}

One relay may be honest-but-curious or actively malicious. Multiple relays may collude. A link observer may see timing and size without decrypting adjacent-link payloads. A global observer may correlate all links. A resource adversary may create many discoveries, duplicates, malformed messages, or candidate responses.

The current Core uses a stable random discovery identifier for loop suppression and accounting. This permits correlation by colluding relays. Consequently, Core v0.1 aims only to prevent one relay from learning the complete route; it does not satisfy the stronger unlinkability statement in the legacy draft.

\section{Protocol overview}

An initiator sends a bounded \textsc{Discover} request to selected adjacent peers. A relay accepts only the first copy for a discovery, records the previous peer, and forwards to a limited number of children while the hop budget remains. Eligible responders may return a \textsc{Candidate} through the recorded reverse state.

As a candidate travels toward the initiator, every relay replaces the child-facing forwarding label with a newly generated parent-facing label and stores a tentative mapping. The initiator therefore receives only a first-hop label rather than the complete path.

The initiator selects at most one candidate and sends \textsc{Commit} through its first-hop label. Each relay activates the tentative forward mapping, installs the reverse mapping, replaces the reverse label for its child, and forwards the commit. The responder returns \textsc{Ready} through the reverse mappings. Only then does the initiator expose the route to a data-plane profile.

\section{State and resource safety}

Every discovery, replay marker, tentative mapping, and active route has a finite local expiration. A node does not depend on a remote close message to recover resources. Each peer and each node has hard limits on concurrent discoveries, forwarding fan-out, candidates, tentative routes, active routes, public-key operations, retries, and retained bytes.

The first-parent rule bounds full discovery state to at most one record per accepted discovery and relay. It also suppresses cycles without disclosing a route vector. The cost is reduced path diversity, which must be quantified in simulation rather than assumed acceptable.

\section{Privacy boundaries}

Hop-local labels prevent a relay from using the forwarding label as a global route identifier. They do not hide predecessor and successor relationships at that relay. Encrypted adjacent links do not hide timing, volume, or peer relationships from a capable observer. Stronger traffic-analysis claims require a named scheduling and cover-traffic profile and an explicit correlation experiment.

The global resolver is deferred because deterministic hash-based lookup tokens can become stable correlation and enumeration handles. A future directory protocol requires its own ownership, freshness, replication, private-query, and denial-of-service analysis.

\section{Evaluation plan}

The first experiments measure discovery coverage, candidate probability, transmissions, duplicate deliveries, and relay state as functions of graph size, degree distribution, hop limit, and fan-out. Subsequent simulations add candidate reverse propagation, commitment, expiration, packet loss, churn, malicious fan-out, candidate spam, replay, and selective forwarding.

A network prototype follows only after state semantics and a concrete cryptographic profile have test vectors. Privacy profiles will then be compared by bandwidth, setup latency, and adversarial correlation success.

\section{Open research problem}

The immediate privacy problem is loop and duplicate suppression without a stable identifier visible to colluding relays. Alternatives include per-hop transformed identifiers, private set-membership mechanisms, or accepting bounded duplicate propagation under strict hop and fan-out limits. The project will compare these alternatives by both amplification cost and collusion leakage.

\section{Conclusion}

Trahens remains a plausible research direction when treated as a small, measurable route-discovery mechanism rather than an immediate replacement for the Internet stack. The project now prioritizes unambiguous state machines, bounded resource use, explicit threat models, and reproducible simulation. Stronger anonymity and global resolution are future layers whose costs and failure modes must be demonstrated rather than assumed.
